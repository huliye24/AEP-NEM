# Glossary

## Core concepts

### AEP (Atomic Engineering Package)
The smallest standard unit of engineering work. A self-contained package that includes task specification, rules, inputs, validation criteria, outputs, and a final report. An AEP can be executed by an AI agent, a human, or an automated system.

> AEP is the engineering atom.

### NEM (Node Evolution Molecule)
An evolvable engineering module composed of multiple AEPs. A NEM represents a node-level capability that can be versioned, upgraded, validated, refactored, depended upon, and reused across AI-native engineering systems.

> NEM is the engineering molecule.

### E-Chain (Engineering Chain)
A connected sequence of NEMs forming a main track or branch track. E-Chains define the topology of engineering work: main lines, feature branches, experimental branches, and fix branches.

> E-Chain is the engineering chain.

### E-Organism (Engineering Organism)
The living project as a whole, composed of multiple E-Chains. An E-Organism grows, evolves, and adapts over time through the continuous addition and evolution of its constituent NEMs and E-Chains.

> E-Organism is the engineering organism.

### PoEW (Proof of Engineering Work)
Verifiable evidence that engineering work was performed. Generated by every AEP execution, containing execution logs, output artifacts, gate results, agent attribution, timestamps, and reproducibility hashes.

> PoEW proves the work.

### Gate (Evolution Gate)
A quality checkpoint that determines whether work passes to the next phase. Gates evaluate acceptance criteria, quality thresholds, stop conditions, and evidence requirements before allowing a NEM to evolve.

> Gate decides evolution.

### Seal (AEP Seal Protocol)
The formal closure layer that checks whether an AEP has complete evidence, accepted gates, known risks, artifact references, and downstream dependency notes.

> Seal closes the work for dependency.

### Industrial Done
The highest AEP completion state. It means the AEP is implemented, verified, reproducible, documented, risk-bounded, and safe for downstream dependency.

## Structural concepts

### Task
A single executable unit within an AEP. Tasks have dependencies defined in `task_map.yaml`.

### Manifest
The `manifest.json` file at the root of every AEP. Contains metadata: AEP ID, version, agent requirements, environment requirements, expected outputs, and stop conditions.

### Track
An alternate name for E-Chain. A track is a linear sequence of NEMs.

### Main Track
The primary E-Chain of an E-Organism. All other tracks branch from or merge into the main track.

### Branch Track
A secondary E-Chain that diverges from a parent track. Used for features, experiments, and fixes.

### NEM-18
A NEM profile composed of three Plan-6 loops: Build-6, Validate-6, and Harden-6. It is used when a node must become runnable, verified, and reusable before downstream adoption.

### E-Chain 54
An E-Chain profile composed of three differentiated NEM-18 nodes: Probe, Build, and System. It is used for campaign-level system transitions rather than isolated node work.

## Maturity levels

### BASIC (v0.1)
Core capability exists. The NEM has completed its foundational AEPs and demonstrates basic functionality.

### STABLE (v0.3+)
Production-ready. The NEM has passed all quality gates and is suitable for use in production environments.

### ADOPTED (v1.0+)
Depended on by other NEMs. The NEM has a stable interface and is a dependency for downstream modules.

### REFACTORED (v2.0+)
Redesigned based on accumulated learning. The NEM has undergone significant structural changes while maintaining its interface contract.

## Execution concepts

### Agent
An executor of AEPs. Can be an AI model, a human, or an automated system. Agents read `agent_spec.md` to understand what to do.

### Dispatcher
The system that routes AEPs to appropriate agents for execution.

### Stop Condition
A condition defined in the manifest that, if met, causes the AEP to halt immediately. Stop conditions prevent runaway execution.

### Acceptance Criteria
Must-pass conditions defined in `validation/acceptance_criteria.md`. An AEP cannot pass its Gate without meeting all acceptance criteria.

### Function Complete
The state where the requested function, artifact, or engineering output exists and can be demonstrated. Function Complete does not mean the AEP is industrially done.

### Evidence Pending
The state where a function exists but required closure evidence is incomplete.

### Seal Review
The formal review stage where PoEW, Gate result, logs, tests, artifacts, risks, and downstream dependency notes are checked.

### Seal Complete
The state where all closure evidence is complete and no blocking risk remains.

### Reopen Required
The state where an AEP must return to implementation or validation because the closure evidence or quality result is insufficient.

### Seal Report
The final closure document that records function completion, PoEW reference, Gate result, evidence bundle, artifact summary, risks, downstream dependency note, reopen criteria, and final decision.

## Network concepts

### Center
An independent publishing authority for AEPs and NEMs. Each center follows the same protocol but maintains its own authority.

### Registry
An optional discovery service for published AEPs and NEMs. Not required by the protocol; any center can operate independently.

### Multi-Center Publishing
The protocol mechanism by which multiple independent centers publish, reference, and collaborate on AEPs and NEMs.
